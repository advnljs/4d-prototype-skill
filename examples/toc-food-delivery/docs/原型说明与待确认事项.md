# 橙子到家 · 一单外卖全流程（4D 原型）说明与待确认事项

> 本文档与原型内“假设与待确认”页同源：第 4 节由 `src/content/notes.ts` 生成（`node scripts/gen-notes.mjs`），测试校验编号一致。
> 品牌、商家、人物、地址、坐标与全部数据均为虚构；支付网关与地图为模拟实现，不连接任何真实系统。

## 1. 原型目的与范围

这是 4d-prototype 方法的 toC 示例：用一个虚构的即时配送平台“橙子到家”，把一单外卖从开店准备、骑手上线、下单支付、接单出餐与派单到店、取餐配送，到收货评价、运营看板，再到次日对账、结算、打款与售后退款冲减的全过程做成可播放、可暂停、可从任一环节进入的 4D 原型，用来和业务、产品、研发一起讨论需求。

- **角色（Who）**：用户、商家、骑手、城市运营 4 类人工操作方；平台服务、智能调度、定时任务 3 类机器操作方；支付网关 1 个外部系统。
- **流程（What）**：17 个环节组成的依赖图（DAG），四行业务分支：商家一支（接单 → 备餐出餐）与调度一支（骑手上线 → 智能派单 → 骑手到店）并行，在“取餐配送”汇合；资金一支从支付流水起（渠道对账 → T+1 结算 → 打款到账）；售后退款在“下期冲减”与结算汇合。结算为“需求必需”，售后退款与下期冲减为“原型补充 · 可选”。
- **数据（Data）**：16 种数据对象，App 界面、库表、接口报文、对账 Excel 按原样展示；订单与资金逐阶段的字段变化与状态迁移。
- **时间（When）**：业务时钟（10:50 骑手上线 → 11:52 下单 → 12:20 送达 → 次日 01:00 对账、02:00 结算、08:00 打款 → 后天 02:00 冲减）；虚拟时钟 0.25×–2× 调速、空格暂停；骑手在地图上随时钟平滑移动。

## 2. 需求摘要（虚构）

为了让示例有“需求原文”可对照，这里虚构一份需求摘要；原型中的“需求必需 / 原型补充”标注与假设编号都以它为准。

| 编号 | 需求 |
|---|---|
| §1 | 用户可浏览附近商家、加购、领取平台券并下单；下单前展示价格明细。支持商家满减活动；配送费按距离与天气浮动。 |
| §2 | 支持在线支付；支付结果以支付渠道的异步通知为准。 |
| §3 | 商家接单后，智能调度为订单选择最合适的骑手；午高峰 30 分钟送达；下单后告知用户预计送达时间；用户可实时查看骑手位置。 |
| §4 | 运营可配置营销券；可查看片区实时指标；异常订单及时预警。 |
| §5 | 按 T+1 与商家、骑手结算，并向商家提供对账文件。 |
| §6 | 用户可对商家与骑手评价。 |

售后退款不在摘要范围内，原型作为补充环节演示（见 C-04）；骑手上线与运力预测、渠道对账、打款到账是摘要没写、但真实业务绕不开的环节，原型按常规做法补上（见 A-07、B-10、B-11）。

### 规则与逻辑（B）

价格、调度、预警、结算与退款的计算口径。

| 编号 | 事项 | 需求怎么说 / 缺什么 | 原型怎么处理 | 体现在 | 需确认 |
|---|---|---|---|---|---|
| B-01 | 商家满减 | 需求写“支持商家满减活动”。 | 满 30 减 3、满 50 减 6，取满足条件的最高一档，由商家承担；计入佣金基数的扣减。 | 用户端结算页 | 商家运营 |
| B-02 | 平台券门槛口径与叠加 | 需求未说明平台券门槛按原价还是优惠后金额。 | 原型按“商家优惠后的商品金额”判断门槛；可与商家满减叠加；同一订单限用一张平台券。情景“优惠门槛”演示原价够、优惠后不够的情况。 | 用户端结算页、方案讨论 | 营销、财务 |
| B-03 | 配送费 | 需求写“配送费按距离与天气浮动”。 | 3 公里内 4 元，超出部分每公里 1 元（向上取整），恶劣天气 +2 元，由用户支付。 | 用户端结算页 | 定价 |
| B-04 | 派单打分 | 需求写“智能调度为订单选择最合适的骑手”。 | 召回 3 公里内（3.5 公里外排除）未满载（< 4 单）的骑手，按距离 40%、负载 25%、顺路 20%、服务分 15% 加权打分，给出可解释的理由；方案讨论页可调权重。 | 三端联动、方案讨论 | 算法 |
| B-05 | 承诺送达时间 | 需求写“下单后告知用户预计送达时间”。 | ETA = 到店与出餐取较晚者 + 交接 0.5 分钟 + 骑行时间 + 上楼 2 分钟；承诺时间 = ETA + 2 分钟，按 5 分钟向上取整。出餐时间按菜品标准时长预估（所以“出餐慢”会超时）。 | 三端联动 | 算法、产品 |
| B-06 | 结算分账公式 | 需求写“T+1 与商家、骑手结算”，未给公式。 | 佣金 = (商品 + 包装 − 商家满减) × 18%；商家应得 = 商品 + 包装 − 商家满减 − 佣金；骑手 = 基础 5 元 + 超距每公里 1 元 + 雨天 3 元 + 等餐超 10 分钟 2 元；通道费 = 实付 × 0.6%；平台净收入 = 实付 − 商家 − 骑手 − 通道费。逐笔勾稽。 | 结算中心 | 财务 |
| B-07 | 部分退款分摊与冲减 | 需求未覆盖售后。 | 退款商品按原价占比分摊本单全部优惠，包装费与配送费不退；商家冲减“商品净额 − 退回佣金”，其余由平台承担；已结算订单在下一结算周期冲减。 | 三端联动 · 售后、结算 | 财务、客服 |
| B-08 | 预警阈值 | 需求写“异常订单及时预警”。 | 骑手原地不动 3 分钟 → 超时预警并按需改派；骑手到店等餐超过 10 分钟 → 催单提醒商家，骑手记等餐补贴；实际送达晚于承诺 → 发 3 元无门槛赔付券。 | 三端联动、运营后台 | 运营 |
| B-09 | 支付回调幂等 | 需求未提重复回调。 | 以网关流水号 trade_no 为幂等键：先查后写，流水表唯一索引兜底；重复回调直接回 ack，不改状态、不重复推送商家。 | 三端联动 · 事件流、方案讨论 | 支付研发 |
| B-10 | 渠道对账口径 | 需求只写 T+1 结算，没有提与支付网关的对账。 | 原型在结算前加一步：次日 01:00 下载网关对账单，与平台支付流水（只记处理成功的回调）按 trade_no 逐笔核对；长款、短款、金额不符挂账转人工，差异订单不进入当期结算。被幂等忽略的重复回调不进入流水，所以不会造成长款。 | 结算中心 · 渠道对账 | 财务、支付研发 |
| B-11 | 打款时间与方式 | 需求写“与商家、骑手结算”，没有说钱什么时候、怎么到账。 | 原型假设结算单生成后次日 08:00 统一打款：商家应得按天合并打到对公账户，骑手收入打到骑手钱包；网关代付回执成功后推送到账通知。失败重试与大额复核原型不演示。 | 结算中心 · 打款到账 | 财务 |

## 5. 运行与验证

```bash
npm install
npm run dev        # PC 版 http://localhost:5290 ；手机版 http://localhost:5290/app.html
npm run typecheck
npm test
npm run build      # npm run preview → http://localhost:5291
```

验收基准：PC 版为 1920×1080 浏览器视口；手机版为 iPhone 16 的 393×852 CSS 视口（在电脑上打开手机版时显示为 iPhone 外框讲解模式）。
