# 单据智能核查助手：原型说明与待确认事项

> 本文用于和业务、信息部、信息安全讨论原型。原型内“假设与待确认”页面与本文第 4 节内容一致（来源：`src/content/notes.ts`，测试校验编号同步）。
>
> 这是 4d-prototype 方法的 **toB 示例**：场景、集团、子公司、客商、制度文件和全部数据均为虚构，不对应任何真实主体。

## 1. 这个原型是什么

虚构的“远帆集团”财务共享中心要做一个**收付款单据智能核查助手**：子公司财务每天录入大量收款、付款、进口结算单据，类别编码、用途说明、金额拆分、交易对方国家/地区填错，会影响往来对账、合并抵销、资金计划和经营分析。原型把需求做成可全程演示、可讨论的样板：

1. **规则库按组织维护**：集团与 6 个区域各自维护一套规则库；核查时按当前用户工号（doc_user_org）匹配所属区域的规则库；每条规则带“大类”和依据（虚构的《资金收付管理制度（2026 版）》条款号、《单据填写规范手册（2025 版）》章节）。
2. **核查数据全部来自上传**：核查岗在界面上传 ERP 导出的三类单据（收款 / 付款 / 进口结算，一个文件多个工作表或分开上传）；RPA 读取供应商协同平台的待付款申请，整理成付款单 Excel 后通过接口上传。两条线走同一流程、同一规则库。
3. **国家/地区一致性并入规则库**：核心是“同一批次内同一境外交易对方的国家/地区应唯一”（三类合并；名称相同用确定性统计，写法不同由清洗 + 相似度聚类 + 智能体否决子公司误合并；平台多站点收付由智能体排除），以多数国别为建议。
4. **结果自动导出并留存**：每次核查自动导出 Excel（各类疑点工作表 + 国别疑点工作表）；在线查看时国家/地区为一个大类。每次核查保存为一个批次，子公司看本公司、区域看辖内、集团看全部。
5. **驾驶舱**：区域看辖内各子公司；集团看各区域并可下钻到子公司。
6. **四类岗位**：集团财务管理员、区域财务管理员（维护规则库 + 一键核查）；子公司财务核查岗、复核岗（一键核查；确认疑点由复核岗执行）。

原型不调用大模型：确定性规则真实执行；需要语义判断的部分按“期望的智能体行为”预设，并完整展示推理轨迹、置信度与误报拦截。

## 3. 关于智能体运行方式的建议

- **分层执行**：完整性、金额勾稽、款项性质、往来类型、审批、区域要求等用确定性代码完成；“读懂用途说明 / 地址 / 名称”的问题交给智能体；同一批次的国家/地区一致性先做确定性统计，写法差异的归并再由智能体否决误合并。
- **语义归并 + 判定缓存**：语义判断的工作量取决于不重复的（类别编码, 规范化用途说明）组合数，而不是单据笔数；按组合判定、结果缓存跨天复用，大模型调用量可降到逐笔方式的一成左右（组合率、缓存命中率为假设值，上线前用历史单据测算）。
- **结论分级**：错误数据 / 疑问数据，各区域可调；低置信度与弱线索一律转人工，人工结论回流判例库。
- **调度**：界面上传为“用户触发 + 后台异步批量”；接口上传由 RPA 定时调用，同一流程；规则库变更由智能体拆解、管理员逐条确认后发布。
- **RPA 的边界**：RPA 只负责从供应商协同平台读取并上传数据，核查与读取解耦；平台是否有开放接口、凭据如何托管仍需确认（Q-01、Q-02）。
